# 单帧观察与运动信息

## 从CartPole到游戏画面，少了什么

CartPole直接提供位置、车速、杆角和杆角速度。截图通常只显示物体当前在哪里；位置相同并不代表未来运动相同。如果决策所需的信息没有进入网络，单纯增加参数或训练次数不能让网络从完全相同的输入中可靠区分两种情况。

下面是假想的静态摄像机游戏场景，只用于手算，不是已测量的Chromium B.S.U.数据。屏幕纵坐标向下增大，玩家中心在y=160，某物体当前在y=120；两帧间隔0.1秒，忽略遮挡、外形方向提示、碰撞体积和加速度。

| 情况 | 前一帧y | 当前帧y | 位移 | 与玩家的关系 |
| --- | --- | --- | --- | --- |
| A | 100 | 120 | +20 | 正在接近 |
| B | 140 | 120 | -20 | 正在远离 |

当前画面都显示y=120，剩余纵向距离都是40像素。但A和B需要不同的风险判断。这里不直接规定具体动作，因为横向位置和其他危险也会影响动作选择。

## 为什么连续观察能补信息

要估计运动速度，先算位置变化，再除以经过的时间。两帧的位置来自观察，时间来自采样间隔：

$$v_y\approx\frac{y_{now}-y_{previous}}{\Delta t}$$

```text
A：(120-100)/0.1 = +200 像素/秒
B：(120-140)/0.1 = -200 像素/秒
```

假设速度暂时不变，再过0.1秒：A到140，B到100。对A而言，到达玩家中心纵坐标的估计时间为40/200=0.2秒；这不是精确碰撞时间，因为例子忽略了碰撞体积与玩家移动。

最小Python对应关系：

```python
previous_y = 100.0      # 上一帧观察到的位置
current_y = 120.0       # 本帧观察到的位置
elapsed_seconds = 0.1  # 两次观察之间的时间
delta_y = current_y - previous_y
estimated_velocity = delta_y / elapsed_seconds
print(delta_y, estimated_velocity)  # 先预测：20.0 200.0
```

前两行是不同时间的测量，第三行给时间尺度；第四行比较两次测量得到带方向位移；第五行把位移换算成单位时间变化。没有参数更新、loss或backward，这里只讨论网络应得到哪些输入信息。

## 输入信息与网络表达能力的边界

仅给当前位置，两种情况都输入120，固定参数的确定性网络得到相同输出。给有序位置对后：

```text
A：[100,120] → 可以识别向下运动
B：[140,120] → 可以识别向上运动
```

实际图像任务可把几张连续画面按时间顺序一起送入网络，称为帧堆叠。它提供历史线索，不代表网络已经自动学会追踪物体。两帧也不保证覆盖遮挡、加速度、隐藏冷却时间等所有信息。

时间间隔同样重要：20像素若发生在0.1秒内，速度为200；若发生在0.2秒内，速度为100。采样不稳定却不给时间信息，会给运动判断带来歧义。先固定采样节奏，再研究复杂处理。

## 相减之前，先确认是同一个物体

如果观察槽 0 每帧放“最近的一颗子弹”，上一帧槽 0 与下一帧槽 0 可能是不同子弹。直接相减会把身份切换当成位移。需要稳定身份匹配，或采用不依赖这种错误配对的观察设计，见 [[概念/游戏内部状态与策略接口]]。

回合重置后也不能把上一局最后位置与新局第一位置相减。复制首帧来填满历史槽，只表示尚无运动证据，不证明真实速度为零。

## 后续环境适配的含义

对于截图观察，需要记录画面裁剪范围、帧的顺序、采样间隔和动作执行时刻。不能把“成功截了一张图”直接当作“观察已经足够用于训练”。第 068 课当时只讨论原则；后续源码状态接口的证据见 [[概念/游戏内部状态与策略接口]]，不能将当时“尚未实现”的描述理解为当前结论。
