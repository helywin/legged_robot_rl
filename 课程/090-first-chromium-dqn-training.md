## 第一段：把游戏的一步变成训练的一步

本段只解决一个问题：Task如何将游戏执行结果转换成训练可用的数据。网络如何学习留到本课第二工作段，不在这里提前堆公式。

### 1. 为什么保留Runtime与Task两层

Runtime负责事实：请求执行哪个游戏动作、推进几次内部更新、收回原始快照。C++进程与Python进程不共享普通Python对象；通信层要编码请求、等待响应、校验请求标识与字段、解析成Python数据。教师负责这些工程和原生正确性。

Task负责解释：从快照选出策略观察、将分数等事实换算为奖励、判断学习任务是否达到外部上限。学习者实现这一层。分开后改变奖励系数只修改任务，不改通信或游戏；训练、评测与GUI回放也能共享同一套任务含义。

一条快照是同一游戏更新边界的状态副本，不是自动持续刷新的对象。读取分数后不能为读取位置又偷偷推进一步；否则同一条观察中的字段不属于同一时刻。观察也不一定包含所有内部信息：`info`用于诊断，不自动喂给网络。

### 2. 固定一组数据，沿整条路径走完

以下为讲解用假设数据，不是游戏采样，也不是首版完整观察/奖励配置。为突出数据流，只保留x坐标；真实策略还需敌机、子弹与资源等信息。

- 动作前：x=2.0，原始分数100，已执行2次决策。
- 动作后：x=2.5，原始分数120，游戏没有自然结束。
- 本例x尺度10.0，每次动作请求5tick，外部上限3次决策。
- 为便于跟踪，本例策略动作4直接映射原生RIGHT=4。正式动作表由任务配置固定，不能只凭两个编号恰好一样建立隐含约定。

先预测：新观察为`[0.25]`，奖励20，决策数3，游戏自然结束为False，外部截断为True。

执行链：

1. 训练循环保存动作前观察`[2.0/10.0] = [0.2]`，策略据此选择动作4。
2. 训练循环调用`task.step(4)`；Task检查是否已经reset、上一局是否结束、动作是否合法。
3. Task将动作索引映射为原生RIGHT，请求`runtime.step(4, 5)`。5是游戏内部更新次数，不是调用Python五次，也不是睡眠五秒。
4. 游戏完成内部更新，Runtime返回同一步后的快照与实际ticks。若途中死亡或关卡完成，实际ticks可以小于请求值，不能凭请求值填写返回值。
5. Task把新x转换为`2.5/10.0 = 0.25`。尺度将典型坐标变成适合比较的数值；它不会修改C++里的位置。这里的10是讲解选择，实际配置要根据场景范围说明。
6. Task计算这次分数增量：`120 - 100 = 20`。100来自Task上次成功保存的原始状态，120来自这次响应。使用总分120会让过去得到的分数在未来每步反复贡献奖励，因此本例取增量。
7. 成功执行一次step后，决策计数`2 + 1 = 3`。本例实际5tick按标称每tick0.02秒相当于0.10模拟秒；决策数仍只加1，不能加5。墙钟耗时需另测。
8. 原生未结束，所以`terminated=False`；决策达到上限，所以`truncated=True`。它们回答不同的问题，不能塞成一个无法区分原因的值。
9. 所有数据验证成功后，Task保存新的原始状态与计数，再返回本次结果。新原始分数120成为下一步计算差值的基准。本例因截断而进入等待reset状态。

算术已使用仓库`.venv/bin/python`执行，输出与预测一致：

```text
old observation: [0.2]
next observation: [0.25]
reward: 20.0
decisions: 3
terminated: False truncated: True
simulated seconds: 0.1
```

这只验证上述算术，不是原生采样或训练证据。

### 3. 返回值到底填什么

设计返回对象`StepResult`的五个字段：

| 字段 | 本例内容 | 来源及用途 |
|---|---|---|
| observation | `[0.25]` | 动作后的快照编码；下一观察 |
| reward | `20.0` | 前后原始分数之差；本次反馈 |
| terminated | `False` | 原生权威终止状态映射；第一关死亡或完成的语义需验证 |
| truncated | `True` | Python任务计数达到外部上限 |
| info | 例如原始分数120、实际ticks=5、决策数3、原因为decision_limit | 人读日志和诊断，不自动进入策略输入 |

这不是把五个值写进一个模糊列表。实现时采用有名字的字段，例如`result.reward`，让调用方明确取哪个值。Python的数据类只是一种组织这些字段的方法；开始写代码时逐项解释构造、类型注解、默认值及可变对象，不要求先猜语法。

`Task.step`不返回动作前观察和动作：调用方已经持有它们。它也不负责把经验放入回放或更新网络，否则GUI回放调用step时也会意外学习。

训练循环把本来持有的旧观察/动作与返回结果拼成经验：

```text
([0.2], 4, 20.0, [0.25], False, True)
 旧观察 动作 奖励   下一观察 自然结束 外部截断
```

### 4. reset与step各自改变什么

`reset(seed)`开始一个新回合：Runtime重置游戏并返回真实开局快照；Task记录它、清零本局计数、允许step，再返回`ResetResult(observation, info)`。还没有执行动作，所以reset不产生动作奖励，也不制造经验。

seed是给游戏随机过程的起始约定，不是给本局打一个编号。只设置Python随机种子不能控制C++游戏；原生reset/seed现已补齐并通过有限轨迹验证；新项目Python接口仍待实现，不能把原生能力等同于Task已实现。

| 操作 | 游戏状态 | Task本局状态 | 回放/网络 |
|---|---|---|---|
| reset | 新局，需重置相关原生状态 | 清零计数，保存新快照 | 不由Task清空或修改 |
| step | 按动作推进 | 替换快照、增加计数、更新是否需reset | 不由Task采样或更新 |
| render | 展示当前画面，不能推进 | 不变 | 不变 |

回合重开通常保留过去经验和已学网络，才能跨多局积累学习；“重新开始游戏”不是“重新开始整个训练”。未来若要重开实验，由训练入口显式创建或清空学习状态。

### 5. 结束边界与错误路径

本例截断时，先保存包含`[0.25]`的经验，再reset。新局即使观察为`[0.0]`，也不能把它填到上一局的下一观察，否则模型会学到动作4从0.2跳到0.0这种虚构后果。

任务结束后再step必须报清楚的错误，不偷偷reset。首次未reset也不允许step。非法动作应在推进前拒绝；通信失败或响应解析失败时，不记为奖励零，不向回放塞经验。因为游戏可能已经执行但响应丢失，不能盲目重发step；把该实例视为状态不可信，交由运行层关闭并报告异常。

Task保存原始快照是为下次计算差值；回放保存观察则是为以后学习。二者不能通过共享一个会被原地修改的列表而相互污染。开始实现时会演示“存入后再修改原列表”的具体后果，再确定复制方式。

## Task实作约定：现在开始亲手实现

入口：`exercises/chromium_dqn/task.py`，四个TODO一起构成完整任务模块；本课内分段实现，不新增课号。原生通信层已经可用。运行方式、字段顺序、返回值及错误条件都直接写在练习文件里。

先理解本轮冻结的task-v1：观察62项，18动作，每步5tick，奖励为分数增量除以100。玩家自身10项、最近4敌机每个3项、最近8敌弹每个5项，合计10+4×3+8×5=62。此版本含玩家资源与外部威胁，但不是全部游戏隐藏状态，也未经训练证明足够通关。

为什么用固定槽位：神经网络每次需要同样长度的输入，而对象数量会变化。排序选择最近对象，多余舍弃，不足补空槽；mask表示这个槽是否真的有对象。排序使用世界距离，不受人为缩放影响。敌机暂时只有位置，没有导出稳定ID；敌弹ID用于打破相同距离的平局，不喂给网络。完整选择和限制写入task.py。

同一组数据手算：玩家在(2,-3)，敌机在(4,0)，相对坐标为(2,3)，该敌机槽为[1,2/20,3/15]=[1,0.1,0.2]。子弹在(1,-2)，每tick位移(0,-0.2)，子弹槽为[1,-1/20,1/15,0/1,-0.2/1]≈[1,-0.05,0.066667,0,-0.2]。没有第二颗子弹时，下一个槽是五个0，而不是复制第一颗。

每个尺度都带含义：位置10和7.5为横纵半范围；相对位置20和15为全跨度参考；生命计数4、damage/shields的500、弹药150按原始含义选参考量级；键盘量20和每tick位移1是首版量级约定，不是最大值。首版不裁剪，所以归一化后的值可以超过1。damage初始-500编码为-1，不能把这个原始字段称为剩余血量。

Python机制：RawSnapshot中的player等是有名字的对象，通过snapshot.player.position读取；position和对象集合是tuple，不能原地修改。encode_observation返回新的list[float]。`-> list[float]`只是类型说明，不会自动生成或转换返回值。`@dataclass`帮我们生成保存命名字段的构造方法，`frozen=True`禁止重绑字段，但并不让字段内部的list自动不可变；所以每次编码仍要创建新列表。

`ResetResult(observation=..., info=...)`明确指定字段，避免猜位置。self是当前GameTask对象，`self._previous`属于这个实例，用于下次分数差；局部变量只用于本次调用。前导下划线表示内部约定，不是Python访问锁。`raise NotImplementedError(...)`是当前脚手架的未完成提示，完成相应函数后用真实逻辑替换，不应在调用方把它吞掉假装通过。

## 第二段：让一批经验真正改变网络参数

Task已有学习者实现与教师补齐/检查证据，按学习者“继续”进入本课第二工作段，不要求重做旧课。当前仍为learning；新网络与更新逻辑尚未由学习者完成。

本段完整实作在network.py与agent.py，独立从零实现。network负责[B,62]→[B,18]，每个输出是相应动作未来累计奖励的估计，不是概率。隐藏层两层64单元为首版容量选择：太小可能表示不出复杂关系，太大增加计算和数据需求；没有声称64最优。每层Linear做输入加权与偏置，ReLU给隐藏层非线性，最后Linear允许负价值输出。

Agent使用独立在线网络和目标网络。在线网络负责当前预测并由optimizer更新；目标网络提供一段时间相对稳定的未来价值估计，在显式sync_target时才复制在线权重。两者结构相同但不能指向同一对象。首次正式训练开始前要同步一次，之后由训练循环定期同步；本次检查器故意提供固定不同权重以便手算，不在构造函数中覆盖它们。

### 固定小数据与来由

这是诊断用人工经验，不是游戏采样。实际输入62输出18，手算缩成输入2输出3，计算机制不变。

| 项目 | 经验一 | 经验二 |
|---|---|---|
| 观察与下一观察（仅诊断） | [1,0] | [0,1] |
| 实际执行动作 | 1 | 2 |
| 当前在线网络对应预测 | 0.5 | 0.2 |
| Task奖励 | 0.2 | 0.4 |
| 下一观察的目标网络三个输出 | [0.8,0.4,0.3] | [0.7,0.6,0.5] |
| 自然终止 | False | True |
| 外部截断 | True | False |

问题是“本次实际做过的动作，其价值应往哪里修正”。第一条经验获得即时奖励0.2，未来最大估计0.8，以gamma=0.9折算：目标0.2+0.9×0.8=0.92。第二条游戏自然结束，所以没有未来收益，目标仅为0.4，不能加0.9×0.7。第一条只是外部截断，任务本身仍可继续，因此保留下一观察估计。这不是对所有任务的通用截断规则，而是task-v1的约定。

只抽取经验实际执行动作的预测，与相应目标比较。经验没有直接证明其他动作的结果，不给所有18个动作同一个奖励标签。计算误差：0.5-0.92=-0.42，0.2-0.4=-0.2；平方变为0.1764与0.04，取平均损失(0.1764+0.04)/2=0.1082。平方使正负误差不能抵消，平均使批量大小变化时尺度较稳定。

### 参数怎么改变

诊断在线网络为无bias线性层，输入是[1,0]或[0,1]，所以选中的输出恰好等于对应权重。平均平方误差对两个选中预测的导数为2×误差/2，因此梯度为-0.42与-0.2；乘输入后，相关权重梯度同样为这两个值，其余为0。

SGD本次学习率0.1，按“旧权重减学习率乘梯度”计算：0.5-0.1×(-0.42)=0.542，0.2-0.1×(-0.2)=0.22。负梯度使权重增加，从而把预测往较高的目标推动。该例其他权重不变只因输入与线性结构特意简化；实际多层网络共享隐藏层，其他动作输出也可能间接变化。SGD只用于可手算的诊断，后续若采用Adam，需要另讲其更新机制，不能把此数值直接套用。

已用仓库PyTorch 2.13.0+cpu验证对应标量自动求导，输出：loss=0.1082000136，梯度约[-0.42,-0.2]，更新后约[0.542,0.22]。末尾差异来自float32表示，不是推导冲突。这个教师诊断验证算术与梯度机制，不能代替学习者Agent.update通过。

### 代码每一步对应什么

1. `online(observations)`执行forward并建立到网络参数的计算依赖；形状[B,A]。
2. `gather`每行选实际动作那一列，得到[B]的预测，仍然保留计算依赖。
3. `torch.no_grad()`内计算目标网络输出、最大值和目标，避免目标分支参与求导。
4. `F.mse_loss`由预测与目标创建标量张量loss。它虽是刚创建的变量，却通过预测的计算图连接回本轮使用的参数。
5. `optimizer.zero_grad()`清除旧梯度；它不清空权重。
6. `loss.backward()`沿图使用链式法则，将导数累加到对应参数.grad；这一步不修改权重。
7. `optimizer.step()`读取它初始化时保存的在线参数引用与这些参数的.grad，执行更新。因此optimizer不需要绑定loss；双方通过同一参数对象及.grad连接。
8. 返回日志时用.item()取Python数值。旧predictions是本轮更新前计算出的值，不会因为权重更新自动重算；下一次forward才使用新参数。

### 动作选择：现在选什么

例如在线网络输出[0.1,0.5,0.2]，贪心动作索引为1。epsilon=0.2表示20%概率进入均匀随机选择分支，80%按当前最大Q值选动作。若随机数0.12，小于0.2，进入随机分支；若0.8，则贪心。随机分支也可能选中动作1，探索不是强制选择另一个动作。

act把一条长度N的观察变成float32的[1,N]张量，第一维保留批次。前向输出[1,A]；argmax返回最大值所在位置，即动作编号，不是最大Q值本身。动作选择不需要反向传播，用no_grad避免构建无用求导图，不修改在线权重、目标权重和更新次数。采样随机状态与探索随机状态分开，避免多抽一次回放改变后面的探索动作序列。

### 回放：把发生过的经验留下

容量3时依次加入A、B、C、D，先后顺序保留为B、C、D。抽两条可能为D、B；抽完库存仍为B、C、D。容量决定记住多少历史，batch_size决定一次用多少条学习，两者不同。无放回指同一次抽样不重复选同一存储位置，下一次仍可以再次选中它。

随机回放减弱连续游戏画面的强相关性，并允许已收集经验再次参与学习；它不会把一条经验内部的时间关系打乱。Transition中的next_observation始终是这条动作之后的状态，与它在抽样批次中排第几行无关。

### 转换批次：整条经验一起移动

假设抽到D、B，使用诊断二维观察：

| 字段 | D | B |
|---|---|---|
| observation | (3,0) | (1,0) |
| action | 0 | 1 |
| reward | 0.3 | 0.1 |
| next_observation | (4,0) | (2,0) |
| terminated | True | False |
| truncated | False | False |

make_batch应生成observations=[[3,0],[1,0]]，actions=[0,1]，rewards=[0.3,0.1]，next_observations=[[4,0],[2,0]]，terminated=[True,False]，truncated=[False,False]。所有字段第0行属于D，第1行属于B，不能分别打乱每列。

观察和奖励是float32，动作用int64以便作为gather索引，结束标志用bool。实际游戏观察从2变为62，数据组织方式相同。观察从Task的list转换成Transition的tuple，防止未来原地修改列表污染历史；make_batch才将数据集中转成张量。不要在回放中保存带计算图的网络预测，否则会保留过时参数关联并占用内存。update时重新计算预测才能使用最新网络。

本段允许使用Python标准库的随机抽样与PyTorch张量构造，不要求手写随机算法或张量底层。亲手实现的是数据生命周期和正确的连接。练习契约与类型注解已在replay.py和Agent.act中；运行`.venv/bin/python exercises/chromium_dqn/check_replay.py`后，需要看到实际连接检查通过才能继续接训练入口。

## 第三段：完整训练循环实作

学习者已修正并完成Replay.sample、make_batch与Agent.act。实际运行check_replay.py通过：人工经验的抽样、批量转换、动作选择与更新连接成立，诊断loss约0.17405、updates=1。这不是原生持续训练结果。

现在的核心实作是train.py的train_loop。配置、启动、关闭、日志与保存推理权重由教师提供样板，循环主体由学习者实现。函数参数、成员类型、返回统计和完整规则已写在.py顶部。

这次要解决的问题是：我们已经会单独采集和更新，如何让它们在多局游戏中持续、按正确顺序运行？训练循环保存当前观察，选择动作，执行一步，用动作前后状态构造Transition，写入回放；条件满足时抽样更新，然后决定下一步继续本局还是重开。网络与回放不随游戏重开而清空。

以诊断配置说明调度：预填充3、批量2、最多更新2次，动作选择前库存不足3时epsilon=1。第1步库存从0到1，不更新；第2步从1到2，不更新；第3步选动作时库存2仍随机探索，存入后变3，开始第1次更新；第4步选动作时库存3，使用后续epsilon，存入后第2次更新，预算达到即停止。前后检查时刻不同，所以不能笼统说“第3步已经不探索”。容量、预填充数量、批量大小、更新次数都是独立概念。

目标网络先同步一次，再按更新次数定期同步。诊断周期2时，第2次更新后同步；期间reset不能触发清空网络。训练总预算停止不等于任务自然终止或外部回合截断，不能修改最后一条经验的结束标志。

日志每步记录决策序号、累计更新、所属回合、奖励、两个结束标志、epsilon和本步loss。没有更新的那一步loss填None；最终summary.last_loss则保留最近一次实际更新的loss。

```bash
.venv/bin/python exercises/chromium_dqn/train.py --check
.venv/bin/python exercises/chromium_dqn/train.py --run
```

默认首轮：单游戏、CPU、每动作5tick；每局250决策；回放容量10000，预填充256，批量32，之后每决策更新1次；最多500更新或5000决策；SGD学习率0.001，gamma=0.99；目标每100次更新同步，epsilon从预填充阶段1变为0.2。正常在第755次决策达到更新预算，会经历至少两个250决策回合衔接。这个短回合设置用于闭环验收，会截断游戏进展，不能直接拿来评价完整第一关能力。正式执行前结合实际吞吐说明耗时，必要调整留在本课记录。
