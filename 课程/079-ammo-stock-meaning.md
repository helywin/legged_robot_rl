# 弹药存量不是子弹数量或剩余开火次数

078资源实作已通过，学习者要求继续。本课只澄清ammo_stock的真实含义，不新增编码或训练操作，不布置机械重复的缩放练习。

## 为什么不能仅凭字段名解释

当前快照player.ammo_stock提供三个float，对应三个武器资源槽。它不是屏幕中飞行子弹的个数，也不是每项还能开火几次。基础0类双发在shootGun的开火间隔满足时生成，不读取库存扣减；只有0类增强分支在gunActive[0]时额外生成子弹并扣库存。1/2类附加武器也各有自己的启用与间隔条件。库存为零不等于基础射击不能开火。

## 同一组数字手算

设三个库存为(150,75,0)，没有双倍开火效果，本次只关注已启用且开火间隔满足的1号武器分支。该分支生成一发1类弹药，并扣ammoStock[1]的1.5。于是关注的库存变化为75-1.5=73.5，其他武器本次不触发时完整元组为(150,73.5,0)。这只是选择该分支解释，真实一次shootGun也可能触发其他分支。

因此75不是“还有75颗子弹”。它是游戏定义的库存单位；一次消耗可为0.5、1.5或特殊模式下的更多值。具体能开火次数还取决于武器种类、激活状态与效果，不能用统一的一库存单位一发来理解。

## 若要编码，参考尺度从哪里来

当前define.h的AMMO_REFILL为150。普通拾取补给路径按此上限夹取，因此可选每项除以150作为候选表达，而不是假设通用最大库存。该样本为(1.0,0.5,0.0)，1号分支执行后第二项为73.5/150=0.49。setAmmoStock本身没有上限夹取，不把普通补给路径上限误说成所有调用的绝对保证。

标准库算术：

```python
stock = 75.0
consumed = 1.5
next_stock = stock - consumed
print(stock / 150.0, next_stock, next_stock / 150.0)
```

前两行指定教学库存与源码分支消耗；第三行模拟该次资源扣减；第四行对比扣减前后的表达。预期0.5、73.5、0.49，本轮实际运行一致。该算术没有驱动游戏生成子弹，也不代表学习者已完成新编码。

## 为什么库存仍不是完整武器状态

源码另有gunActive和gunPause，分别决定附加武器是否启用、间隔是否满足。当前快照未导出这两组字段，库存数值不是完整开火状态。正常拾取会启用武器；清理仅在库存严格小于0时将其归零并禁用，不能把零库存与gunActive=false无条件等同。

所以后续可以把三项库存作为观察候选，但这不等于已经完整描述武器状态。本轮仍保留17项观察布局，不擅自添加库存，下一步讨论正式接口需要哪些信息时再接入与验证。策略是否应节省附加资源，还取决于动作接口是否允许相应控制及奖励目标，不能由字段存在直接推导。
