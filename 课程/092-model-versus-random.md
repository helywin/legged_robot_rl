# 模型比随机策略好吗

本课实作已完成：学习者实现逐局评测，教师按要求补全汇总并修正统计问题；检查通过后学习者运行了模型/随机各20局对照。观察、动作、奖励与网络都已完成，不重写它们。教师负责启动、载入、选择策略回调、文件保存和清理。核心TODO不预填答案。

## 为什么要比较

模型能运行不等于学到了有用行为，随机开火也可能得分。先以固定任务规则比较，回答“模型在这组开局里，是否比同权限随机动作更有用”。选择动作是唯一比较因素，网络冻结，不继续优化。

规则冻结：指定第一次训练的policy.pt；task-v1、62维观察、18动作、每动作5tick、保存配置中的每局250决策上限；模型贪心，不探索；随机策略均匀选18动作。双方各20局，共用游戏种子201..220；随机动作单独使用100000+对应游戏种子初始化。每局reset清除状态，模型与随机各自使用独立运行时实例。种子配对不保证不同动作下出现完全相同弹幕，只控制起始随机条件；支持范围仍限已验证的本机构建和配置。

40局最多10000决策（50000原生tick），不逐步绘图但仍依赖显示服务，预计秒级到几十秒，具体记录elapsed_seconds。此次上限较短，是受限任务比较，不作为完整单关或完整游戏验收。

## 两个函数各干什么

`evaluate_episode(task, choose_action, seed)`：reset一次，读取观察，交给choose_action得到动作，step并累计统计，用新观察继续；任一结束标志为True就返回。choose_action是传入的函数，它已经封装模型/随机选择，所以同一个循环公平服务两种策略。不能偷偷reset多次直到刷出高分。

返回该局原始得分、累计任务奖励、成功决策数、实际ticks×0.02的模拟存活时间、可见生命计数下降总量及结束原因。最后一步可能不足5tick，所以不能简单用决策数×5代替实际ticks。Task.info新增lives_counter作为诊断字段，原生已有此事实，不改变网络输入或奖励。

生命统计例：4→5→3，各步下降量为max(0,4-5)=0、max(0,5-3)=2，总下降2。首尾相减只得到1，会漏掉中间的损失。这仍只是快照可见下降，若同一步奖励生命抵消损失就无法还原精确事件，不称为死亡事件数。

`summarize(rows)`：统计局数、平均与中位得分、平均模拟时间、平均生命下降、完成/死亡/截断率。得分[0,100,900]时平均333.333，中位数100；两者一起看有助于识别少数高分带来的偏差。完成率只数level_over，hero_dead为死亡，decision_limit为截断，不能把“没有死”全部算成功。

## 实现与结果边界

完整类型、字段名、输入输出、规则和运行方法都写在exercises/chromium_dqn/evaluate.py中。诊断检查使用两步人工环境，验证新观察、最后实际tick、只reset一次和先加命后减命统计；不假装原生评测。

```bash
.venv/bin/python exercises/chromium_dqn/evaluate.py --check
.venv/bin/python exercises/chromium_dqn/evaluate.py --run
```

输出runs/eval-*/config.json、episodes.jsonl、summary.json，包含检查点及源码哈希、种子和汇总。模型参数前后应保持不变。若模型输了或结果接近也如实记录，不能临时换种子、上限或挑选最好几局。20局结果只支持这组有限样本结论；不直接声称普遍优于随机，更不能据此宣称通关。
