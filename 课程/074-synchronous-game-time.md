# 同步游戏里读取、推进与等待的区别

长期目标仍是用 DQN 控制 Chromium B.S.U.。本课接续已完成的人工操作和已确认的 Python 状态读取，只研究：Python 等待时，游戏是否继续变化？

## 先分清谁让时间前进

普通游戏像一直播放的电影，Python 晚一点读取就会看到更晚的状态。同步模式像由你逐格翻动的动画：程序要求推进，游戏才计算下一格。这里一格称为 tick，即一次完整的内部游戏更新。

以下区别只针对 `GameClient(synchronous=True)`：

| 操作 | 读取或改变什么 | 游戏步数变化 |
|---|---|---|
| `game.snapshot()` | 读取当前状态 | 0 |
| `time.sleep(2)` | Python 等待现实中的两秒 | 0 |
| `game.step(Action.RIGHT, ticks=1)` | 应用右移输入并更新整个游戏 | 通常 +1 |
| `game.step(Action.IDLE, ticks=1)` | 释放控制输入并更新整个游戏 | 通常 +1 |

回合已经结束时不能继续 step；一次多步请求遇到终止会提前返回，要看 `actual_ticks`。IDLE 并不暂停世界：敌人和子弹仍更新，飞机原有控制累积量还可能继续衰减。

## 一组数字走到底

设当前 `episode_tick=10`，游戏尚未结束。读取一次得到10，等待现实中的2秒，再读仍是10。请求右移3步，返回13；随后请求IDLE一步，返回14。

当前接口每tick使用0.02秒的参考游戏时间，因此开始为 `10×0.02=0.20` 秒，右移后为 `13×0.02=0.26` 秒，IDLE后为 `14×0.02=0.28` 秒。中间真实等待的2秒不会加进参考游戏时间。它也不代表一次计算在电脑上必须耗时0.02秒。

可以先用标准库算术确认计数预期：

```python
tick = 10
print(tick, f"{tick * 0.02:.2f}")
# 读取和等待都没有游戏推进指令，所以不增加 tick。
tick += 3
print(tick, f"{tick * 0.02:.2f}")
tick += 1
print(tick, f"{tick * 0.02:.2f}")
```

第一行设定起始计数；每个print只展示已有数字；两次加法分别代表实际执行3步和1步。预期输出为 `10 0.20`、`13 0.26`、`14 0.28`。这只是计数模型，游戏是否遵守规则要用下面的真实实验检查。

## 对应真实代码

已有 `watch_steps.py` 的每轮先调用 `game.step(action)`，执行一个完整tick，再从返回结果打印步数与位置，最后 `time.sleep(args.delay)` 留时间供人观看。等待不会被传给游戏。每段动作结束后，脚本保存快照、等待2秒、再读快照，用相等比较检查等待期间状态是否改变。

脚本还会先执行一次IDLE，再依次执行四段动作，每段12步。因此正常未提前终止时，第一条right输出tick=2，最后为49。`--delay`不会改变这些计数。没有固定随机种子，不要求两次运行的敌人、子弹和分数完全一致。

## 亲手实验

继续已有 [[experiments/2026-09-07-chromium-synchronous-step/README|同步游戏时间对照实验]]，不新增重复练习。1个游戏窗口、0次网络训练；每次正常执行49tick，预计十几秒至半分钟内结束（含窗口启动）。

在仓库根目录依次运行，仅改变等待时间：

```bash
.venv/bin/python third_party/chromium-bsu-rl/examples/watch_steps.py --delay 0.02
.venv/bin/python third_party/chromium-bsu-rl/examples/watch_steps.py --delay 0.15
```

成功条件：第二次观看更慢，但tick序列不因等待增加；每段2秒等待期间状态不变，输出 `Snapshot unchanged: True`。学习者需要实际比较并报告现象；仅运行一次教师演示不算完成受控实验。如果出现异常，保留输出，先定位再推进。
