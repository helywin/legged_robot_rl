# Chromium 源码入库与 Python 训练接口方案

2026-09-07进度：用户已确认Python能打印状态。同步GUI step原型现已实现，C阶段部分完成：动作、精确tick、等待冻结与提前结束有原生检查证据；每tick仍绘图，完整更新/渲染拆分、seed/reset、无渲染加速和训练尚未完成。见 [[experiments/2026-09-07-chromium-synchronous-step/README]]。使用独立公开仓库和Git子模块：`https://github.com/helywin/chromium-bsu-rl`。课程仓库不直接维护游戏文件。

## 1. 要交付什么

在独立的`chromium-bsu-rl`仓库维护 Chromium B.S.U. 源码和Python接口，本课程仓库通过子模块引用固定提交。增加受 Python 控制的训练模式：Python 发出动作，游戏精确推进约定数量的逻辑更新，返回同一时刻的状态与事件；保留原生 GUI 供首次演示和策略回放。

首版目标是可解释、可重复的环境闭环，不是立刻通关。暂不做截图识别、桌面按键注入、多机训练或机器人部署；不覆盖系统已安装的 `chromium-bsu`，不修改用户游戏存档。

## 4. C++ 与 Python 怎样连接

首版选择：**每个环境一个C++子进程，标准输入/输出使用逐行JSON请求响应（JSON Lines）**。

理由：原游戏使用大量全局状态，不适合先在一个Python进程里建立多个实例；子进程隔离较清楚，也免去首版Python扩展的ABI与绑定构建问题。暂不采用socket服务、共享内存或pybind11。若测量表明序列化成为瓶颈，再单独评估更换传输层。

- Python用标准库`subprocess`启动绝对路径的教学版，禁止`shell=True`。
- C++将所有普通日志改发stderr；stdout只允许协议消息并及时flush。
- 请求含`protocol_version`、`request_id`、`command`；响应含匹配ID、成功结果或结构化错误。
- 命令：`hello`、`reset`、`step`、`snapshot`、`render`、`close`。同时最多一个未完成请求，不提供自动重试step，避免动作执行两遍。
- `hello`返回构建身份、协议/控制模型/观察版本和能力，如`gui`、`headless`；不能把没有实现的能力标真。
- 有响应超时、消息长度限制、非法动作检查、EOF和进程崩溃处理。协议异常抛Python异常，不伪造训练经验或终止奖励。
- GUI事件在主线程处理；等待Python指令时仍泵送窗口事件，但不推进游戏。窗口关闭通知客户端中止实验；暂停仅影响查看，不让一次step无声少执行。
- `close()`可重复调用；仅回收客户端自己创建的子进程，超时先终止再强制结束，不扫描或杀死其他游戏。
- 原游戏未必已有JSON库。实施时优先检查环境，若引入小型C++JSON解析库，固定版本、记录许可和摘要；不手写不完整的JSON解析器。本轮不安装依赖。

Python接口依赖由独立仓库的`pyproject.toml`管理，可脱离课程仓库安装。课程运行仍用本仓库`.venv/bin/python`；实施时在课程`pyproject.toml`声明集成依赖，并记录从子模块本地安装的复现命令。构建不硬编码课程或个人路径。C++依赖另写清检查步骤，不借机升级系统或Isaac Lab。

## 5. Python 的使用外观

以下是目标API示意，当前不能运行：

```python
from chromium_rl import ChromiumEnv

with ChromiumEnv(render_mode="human") as env:
    observation, info = env.reset(seed=7)
    action = env.action_space.sample()
    next_observation, reward, terminated, truncated, info = env.step(action)
```

- 创建：启动一个环境进程，不立即训练。
- reset：返回新局第一项观察；不清空Python模型、optimizer或回放缓冲区。
- step：动作→推进→状态快照→Python编码观察和计算奖励；没有隐式重开。
- render：展示最新状态，不进行逻辑更新；可多次调用，状态摘要必须不变。
- Python公开接口和`info`核心字段有明确类型，避免把所有返回值写成`Any`。

分两层交付：先实现返回类型化原始快照的`GameClient`；再由`ChromiumEnv`提供固定形状观察及Gymnasium接口。原始可变长对象列表不是可以直接送入DQN的张量。

## 6. 动作与逻辑更新的契约

候选首版动作集合为9种移动×开火开关，共18项：

- 移动序号固定为：不输入、上、下、左、右、左上、右上、左下、右下。
- 动作编号约定为`movement_index + 9 * fire`；例如3表示左移不开火，12表示左移并开火。
- 所有动作都设置完整方向及开火状态，不是累积按键命令；相反方向组合不开放。
- “不输入”是释放方向控制，不是瞬间清零内部速度。保留原速度累积、衰减、整数化和边界限制；保留原来的斜移行为。
- 将键盘路径中的方向状态计算提取为共享函数。方向从未按到按下的增量只在边沿触发，相邻两个相同动作不重复触发首次按下。
- OS键盘重复事件不进入训练路径。采用固定逻辑tick上的确定性输入规则，并单独命名控制版本；与人工路径的差异（尤其重复按键）必须记录和对照，不宣称逐帧完全等价。
- 首次接口验证`frame_skip=1`；通过后才单因素比较动作保持tick数。该值初始化后固定，写入配置和模型契约。

每个tick的边界定义：上次快照→应用当前控制→按固定顺序更新游戏→产生事件与新快照。渲染、睡眠、Python推理耗时不参与推进。固定`speedAdj`等影响逻辑的参数，记录其值，不把原来的墙钟自适应当作训练物理时间。

必须检查绘图、过场、音频等代码是否消耗随机数或修改游戏状态；不能只搬动一个update代码块就声称已完全解耦。GUI和无窗口路径应共享同一逻辑更新函数。

## 7. 导出哪些状态

原始快照在一次更新完成后整体复制，包含`episode_id`、单调`tick_id`、关卡、模式及以下数据，不导出裸指针：

| 数据 | 用途和限制 |
|---|---|
| 玩家位置、内部键盘速度、当前按键/开火状态 | 观察与诊断；键盘速度不是世界坐标速度，两者分开命名 |
| 生命、伤害、护盾、弹药、武器冷却与临时状态 | 区分移动、可开火能力和生存状态；具体字段逐项核查 |
| 敌机、敌弹、道具及必要的我方子弹 | 对象ID、类别、位置、运动信息、大小等；ID在一局内稳定，不复用内存地址 |
| 原始累计得分、关卡及游戏模式 | 奖励来源和阶段诊断；不得用屏幕OCR代替已有内部字段 |
| 本步事件及实际执行tick数 | 击毁、漏敌、损命、受伤、过关等；只累计本次step，避免重复计数 |

位置以游戏世界坐标返回，明确轴方向和单位；不是窗口像素。不同敌机的`vel`字段不一定覆盖其完整运动规则，先核查各类型；必要时用实际相邻tick位置差导出实测移动量，不能把无效字段标成精确速度。

事件在实际发生处记账；不能只用`lives_before-lives_after`推断损命次数，因为同一步可能既加命又损命。对象死亡、得分及关卡事件也要避免重入计数。

策略观察首选结构化向量：玩家字段＋有限数量的敌机/敌弹/道具槽位＋有效掩码。对象筛选按明确的威胁/距离规则稳定排序，补零位置由掩码区分；超额截断记录数量。K值、字段、归一化尺度和最终维数在实际快照调查后冻结成`observation_v1`，未冻结前不开始DQN。不得宣称有限槽位已经涵盖完整游戏状态。

原始快照可有诊断字段而不输入策略。明确区分“游戏知道”“训练器使用”“策略实际看到”。结构化输入路线的结果不能称为纯视觉策略通关。

## 8. 奖励、结束和重置

首版可核对奖励采用原始得分增量：`reward = score_after - score_before`。C++只报告得分与事件，Python奖励函数负责计算。损命惩罚、存活奖励等后续再做单因素实验，不提前叠加多项。每步同时保留原始分数与训练奖励，失败模型也留记录。

终止语义：

- 整局模式下，仅确认的整局失败或最终完成置`terminated=True`；`LevelOver`只是阶段变化，不自动终止整局。
- 第一阶段只验证固定一关时，必须显式使用`task_mode="single_level"`，该模式的过关才是终止；产物明确标为单关任务。
- 原生命计数出现`lives < 0`判定，不能未经解释直接套`lives==0`；核对显示生命与内部备用战机计数含义。
- 外部tick预算耗尽置`truncated=True`；预算按实际逻辑tick而非Python调用次数统计。
- 自然结束立即停止剩余动作重复，返回真实结束快照和`executed_ticks`，不跨到新一局。截断保留真实最终观察供后续target处理。
- 整局模式下跨关/复活需明确的确定性推进路径，过场不混入“飞机可控”的普通动作；最终关判据尚未冻结，不能借`LevelOver`宣称通关。未实现前拒绝该模式，不静默退化为单关。

reset顺序与范围：先设置目标关卡和难度，再调用适配后的初始化；清理对象、计时、模式、过场标记、按键速度、开火、冷却、事件队列、对象ID及Python历史。将随机数表、游标及其他随机来源统一纳入seed。隔离用户配置和高分，训练模式不写真实高分或解锁进度。

先以新建子进程作为干净重置的对照，再验证进程内reset是否一致。固定seed保证的范围先限定为相同构建和逻辑配置，不预先承诺跨平台位级一致。

## 9. GUI、无界面与性能边界

2026-09-07补充要求：**加速运行是进入正式训练前必须验证的能力，不能按原游戏实时速率收集全部经验。** 本节替代“只在将来考虑性能”的理解。本轮仍仅修改方案。

### 9.1 分开三个时间量

| 量 | 拟定契约 | 含义 |
|---|---|---|
| `simulation_dt` | 首版基准0.02秒，运行中不可改 | 每个逻辑tick代表的游戏时间；依据`MainSDL.cpp:240`附近原逻辑基于50fps的说明，仍需基准轨迹核对 |
| `action_repeat` | 与前文`frame_skip`同义，Python正式接口统一使用此名；初验1 | 一个决策维持多少个完整逻辑tick，不减少中间碰撞与事件检查 |
| `playback_speed` | 仅GUI查看使用，默认1；训练不限速 | 墙钟播放速度，不进入游戏状态更新公式 |

训练初始固定`speedAdj=1.0`，一个tick保留原50fps基准下的完整离散更新。增加单调`episode_tick`以及`simulation_time = episode_tick * simulation_dt`；不使用过关时会清零的`gameFrame`计算整局时间。返回`executed_ticks`与`elapsed_sim_time`，便于识别提前结束的动作。

原游戏不是所有代码都接收`dt`的统一物理引擎。首版`simulation_dt`用于明确基准时钟，并不意味着把常量改大就能安全改变全部更新：键盘速度衰减、整数位移、发射冷却、敌机生成和过场计时可能分别按tick或`speedAdj`计算。必须建立时间依赖清单，移除训练路径对SDL墙钟/FPS校准的依赖。

例如基准50tick/s时，游戏内10秒需要500tick；若电脑能在墙钟0.5秒内执行完相同500tick，就是20倍实时速度。游戏中的子弹每步仍走原来的距离，碰撞检查仍执行500次。这个20倍只是说明算法，不是已测性能。

### 9.2 加速实现顺序

1. 训练模式移除`SDL_Delay`及其他实时限速，绕开原FPS启动校准和自动`speedAdj`调整；禁止渲染垂直同步阻塞逻辑推进。
2. 正式采样关闭渲染和音频；先实现不绘制路径，再验证是否能完全去除GL上下文依赖。GUI按独立显示频率刷新，可跳过显示帧，不跳过逻辑tick。更快的训练不应要求窗口也每tick刷新。
3. `step(action)`在C++内部执行`action_repeat`个完整tick，只在决策边界进行一次请求响应，按tick收集事件；终止或预算截断立即停止。同一动作重复多tick可以减少推理/通信开销，但会降低控制决策频率，不把它当成无代价优化。
4. 用固定动作轨迹分别测量纯C++推进、Python接口采样、带DQN更新的端到端吞吐。根据瓶颈再优化序列化、观察构建或独立环境进程，不提前引入大型并行框架。

训练路径等待Python决策时冻结游戏逻辑，GUI仍处理退出事件。多个环境并行也不能按各自墙钟推进，否则CPU负载不同就会生成不同游戏规则。

### 9.3 为什么不直接把time step乘10

把单步时间从0.02秒放大到0.2秒，可能让子弹在一次更新中跨过飞机；按tick触发的敌机生成或开火冷却也可能与移动速度失配。这不是单纯提速，而是换了任务。

首版不开放任意`simulation_dt`。将来确需更大外层时间步，优先执行多个0.02秒内部子步；减少内部子步数则属于单独的近似模型实验，须验证连续碰撞或等效检测、所有计时器以及策略行为变化，并提升环境版本。不能只放大`speedAdj`。

`action_repeat`在检查点中冻结，训练与评估保持一致。增大它时同步说明奖励聚合、探索衰减和更新频率的计数单位，不能沿用未解释的超参数。首版DQN折扣定义为每个决策步，保持固定重复数；若以后改为每tick折扣，则需同时实现步内折扣奖励与`gamma_tick ** executed_ticks`的未来项，不能只替换指数而不改奖励。

### 9.4 加速验收（正式长训练前完成）

- 同一构建、seed、逻辑配置和预录动作序列，对比慢速GUI回放、GUI不限速、无渲染不限速；在相同tick比较玩家、对象、事件、奖励及结束原因。整数/离散状态一致；浮点若需容差，先明确范围并报告最大差异，不拿容差掩盖不同碰撞结果。
- 另外在两次step之间插入人为等待，验证只增加墙钟耗时、不改变逻辑轨迹；多次render也不得改变随机游标或状态。
- 先短测10000tick（跨回合时记录每次reset，累计实际tick），预热与reset耗时分别列出；若机器太慢则缩小短测规模，不自动启动长任务。
- 报告`logic_ticks/s`、`decisions/s`、`gradient_updates/s`、通信耗时和墙钟耗时。实时倍率定义为`实际tick数 × simulation_dt / 墙钟秒数`，分别列纯环境与端到端结果。
- 工程目标先设单环境、无渲染纯采样至少10倍基准实时速度（即至少500tick/s），这是待测目标，不是性能承诺；若达不到，先给性能剖析和改进结果，不能直接启动大规模训练。带DQN更新的倍率单独报告，不混用纯游戏基准。
- 加速正确性、无渲染能力、性能目标分别验收。取消sleep但仍被绘制/通信卡住不算性能验收通过；加速后轨迹变化也不算正确性通过。

### 9.5 GUI与真正无界面的边界

先交付GUI同步模式：Python没发step时游戏逻辑不跑，但窗口可以刷新、关闭。回放可限速方便观看，训练不按墙钟限速。

无窗口模式是独立里程碑：需要确认初始化、字体、纹理、音频和对象更新不依赖有效GL上下文。隐藏窗口或虚拟显示不能冒充真正无图形依赖。首版若仍需图形上下文，文档明确说明，不提前承诺服务器可运行。

暂不支持同进程多实例；后续可多个独立子进程并行。先测量每秒tick、协议时间、状态大小及GUI开销，再决定是否换传输格式。

## 11. 关键决策与暂不承诺

- 决定：源码与Python接口在独立公开仓库维护，课程以submodule固定提交集成；C++独立子进程；逐行JSON；Python提供Gymnasium外观；先结构化观察和GUI。
- 决定：保留移动计算，不直接设置位置；训练模式禁用墙钟自适应及外部人工控制，GUI只允许查看/暂停/退出。
- 决定：以0.02秒为拟定固定基准逻辑步，训练不限速运行；不通过放大time step或speedAdj冒充等价加速。加速正确性与性能是正式长训练前的门槛，见9.1～9.4。
- 待实施调查：最终关卡完成判据、完整随机来源、重复按键对照、渲染副作用、对象槽位数量、真正无窗口构建依赖。
- 暂不承诺：纯视觉通关、原版与教学版逐帧完全等价、多环境吞吐、最终通关成功率。

阶段A已取得源码导入、编译和GUI启动证据；输入法环境下的模拟字母键退出未可靠验证，不推断游戏退出处理有错。阶段B实现玩家/敌机/模式的原始快照，用户已确认能打印状态，见 [[experiments/2026-09-07-chromium-live-snapshot/README]]。阶段C已交付同步GUI原型：动作先于完整更新，等待不推进，每步固定speedAdj=1，结束提前停止。7项开发者检查通过，GUI已见飞机右移和子弹。原版绘图仍有逻辑副作用，因此每tick仍绘图，完整拆分与真正无渲染是下一工程工作。尚无seed/reset、子弹快照、事件或稳定对象ID，不称为完整训练环境。
