# 只增加训练预算：500与4000次更新对照

## 问题与假设

093发现代表局长期贴边且最终死亡。先检验训练量不足这一候选解释：保持任务与算法相同，增加更新预算是否改善评测行为？不预设提升，也不同时添加损命惩罚。

## 冻结配置

- 环境：原生Chromium，单游戏进程、CPU、seeded-reset-v3；不逐步绘图训练仍需要显示服务。
- 基线：train-06fbbc3a5a1c4ff78afc7ffabb1586c1/policy.pt，500次更新；其评测为eval-9ace3fa7a619421d849f1cad55475f8a。
- 候选唯一配置变化：max_updates由500变4000；从头训练，不加载推理权重续训。
- 固定：max_decisions=5000，episode_limit=250，capacity=10000，batch_size=32，learning_starts=256，target_sync_every=100，epsilon=0.2，gamma=0.99，SGD学习率0.001。
- 种子固定：game_seed=31、network_seed=7、replay_seed=7、exploration_seed=11。观察62维、动作18种、每动作5 tick、task-v1奖励不变。
- 预计4255次决策、4000次更新；按首训速度预计几十秒，实际耗时记录。增加预算同时带来更多采样和更新，不能解释成只对同一批数据多做优化。
- 评测冻结：最终权重，不挑中间最佳；模型/随机各20局，游戏种子201..220，随机动作种子100000+游戏种子；每局250决策上限。20个种子已用于开发诊断，不作为最终独立验收。

## 学习者操作与完整命令

```bash
.venv/bin/python exercises/chromium_dqn/train.py --check
.venv/bin/python exercises/chromium_dqn/train.py --run --max-updates 4000
```

训练完成后直接复制终端打印的“评测本次权重”完整命令执行。形式如下，其中路径必须使用本次输出，不能直接运行默认evaluate.py而再次评测旧权重：

```bash
.venv/bin/python exercises/chromium_dqn/evaluate.py --run --checkpoint exercises/chromium_dqn/runs/train-本次实际编号/policy.pt
```

有效实验条件：实际4000次更新、4255决策，参数有变化；保存配置仅max_updates与基线不同；评测冻结参数且各20局完成。原版保留为对照，不覆盖旧检查点。

## 结论与下一步

新训练与评测已完成：平均分增加895，但中位分下降87.5，平均存活减少1.758秒，20局全部死亡。不能称为生存能力改善。优先同时检查中位得分、存活时间及死亡局数；只涨平均分而生存变差应如实说明取舍。总训练奖励不可直接比较（候选训练更久），训练loss下降也不能代替评测。

如果没有提升，结论是“本种子和预算下增加训练量没有改善”，不是“训练再久都没用”。不在看到结果后无限追加预算或改评测规则。下一课095处理训练随机性和候选复核；最终应使用未参与选择的种子验收。

源码发现：`third_party/chromium-bsu-rl/game/src/PowerUps.cpp:228—243`在道具y<-12且游戏进行中时，按道具类型加2500或10000分（SuperShields还加命）。所以原始得分不仅来自击杀，道具落出屏幕也可产生任务奖励25或100。该规则是静态源码证据；当前逐步快照没有得分来源事件，不能仅凭分数吻合断言某一笔奖励来自此分支，更不能证明它是策略单一化的唯一原因。

下一步先解释总分反馈与期望行为的差别，再决定如何区分得分来源。不要直接加“必须移动”或“禁止角落”的奖励，也不自动追加训练。若需要区分击杀与道具得分，应先完善并验证原生事件接口，再由学习者实现任务奖励；C++修改按既有要求单独提交推送。本轮仅源码检查，没有修改C++。
